# Development Plan Writer

개발 전에 계획을 상세하게 정의해 누락된 정보, 잠재 리스크, 선후행 이슈를 미리 드러나게 만든다. 목적은 문서를 빨리 만드는 것이 아니라, 실제 개발 과정에서 추가 이슈를 줄이고 작업이 막히지 않도록 준비도를 높이는 것이다. 범위가 크면 단일 문서가 아니라 `전체 계획서 1개 + DAG 기반 세부 계획 문서 묶음`으로 설계한다.

## 작업 흐름

### 1. 계획서 유형을 정한다

- 요청을 `신규 기능 개발`, `리팩토링`, `마이그레이션`, `시스템 연동`, `운영 개선` 중 하나로 분류한다.
- 유형별 예시는 아래와 같다.
  - `신규 기능 개발`: 관리자 대시보드 추가, 결제 취소 기능 개발, 검색 필터 기능 출시
  - `리팩토링`: 회원 도메인 서비스 구조 정리, 공통 인증 모듈 분리, 레거시 쿼리 계층 개선
  - `마이그레이션`: 구 DB에서 신 DB로 이전, VM 환경에서 Kubernetes로 전환, 레거시 인증 방식에서 OAuth2로 전환
  - `시스템 연동`: 외부 결제 API 연동, CRM과 회원 데이터 동기화, 사내 시스템과 SSO 연결
  - `운영 개선`: 배포 자동화 구축, 장애 알림 체계 개선, 로그 수집 구조 정비, 반복 운영 작업 자동화
- 유형이 애매하면 사용자 표현을 우선하되 문서 구조는 가장 가까운 유형을 따른다.
- 구조 선택이 필요하면 `references/plan-template.md`를 읽는다.
- 범위가 크거나 다수 팀, 다수 시스템, 장기 일정이 포함되면 처음부터 `전체 계획서`와 `세부 계획`을 분리한다.

### 2. 컨텍스트를 수집한다

- 가능하면 관련 `README`, issue, PRD, 설계 문서, API spec, 코드 구조를 먼저 확인한다.
- 아래 항목을 최소 단위로 채운다.
  - 목표
  - 범위
  - 제약
  - 일정
  - 의존 시스템 또는 팀
  - 성공 기준
- 정보가 없으면 추정해서 단정하지 말고 `가정`, `미정`, `확인 필요`로 명시한다.

### 3. 필요한 질문을 충분히 한다

- 정확한 정의를 위해 필요한 경우 질문 수를 제한하지 않는다.
- 불확실한 부분은 추측으로 메우지 말고 확인 질문으로 드러낸다.
- 바로 답을 받기 어려운 항목은 문서에 `가정`, `미정`, `확인 필요`로 분리한다.
- 항상 `확정 사항`, `가정`, `오픈 이슈`를 구분한다.

### 4. 계획서를 작성한다

- 기본 순서는 `배경 -> 목표 -> 범위 -> 접근 방식 -> 단계별 실행 계획 -> 리스크 -> 검증/배포`로 둔다.
- 작업 단계는 추상 문장 대신 구현 가능한 단위로 쪼갠다.
- 일정이 불명확하면 절대 날짜 대신 `단계`, `주차`, `이정표` 단위로 쓴다.
- 배포가 포함되면 테스트, 롤아웃, 모니터링, 롤백을 넣는다.
- 템플릿이 필요하면 `references/plan-template.md`를 읽고 필요한 부분만 남긴다.
- 큰 계획은 아래 구조를 기본값으로 둔다.
  - `전체 계획서`: 전체 목표, 범위, 이정표, 핵심 의존성, 최종 산출물 정의
  - `세부 계획 문서`: 세부 작업 노드 문서. 각 문서는 DAG의 노드 또는 노드 묶음 역할을 한다.

### 5. DAG 구조를 강제한다

- 세부 계획 문서는 반드시 방향 비순환 그래프(DAG)로 연결한다.
- 각 세부 문서는 최소한 아래 항목을 가진다.
  - 문서 ID
  - 상위 마일스톤 또는 상위 목표
  - 선행 문서
  - 후행 문서 또는 인계 대상
  - 입력물
  - 산출물
  - 완료 조건
- 순환 의존성이 생기면 문서를 다시 분해하거나 공통 선행 노드로 끌어올린다.
- 리프 노드 문서는 실제 검증 가능한 산출물을 가져야 한다.
- 모든 리프 노드의 산출물은 전체 계획서의 목표, 이정표, 최종 산출물 중 하나에 추적 가능해야 한다.
- 이 추적 관계가 불분명하면 계획서가 아니라 작업 메모에 가깝다고 보고 다시 쓴다.

### 6. 계획서를 검토한다

- 각 실행 단계가 목표와 직접 연결되는지 확인한다.
- 범위 밖 항목은 `비범위`로 분리한다.
- 리스크마다 탐지 방법 또는 대응책이 있는지 확인한다.
- 최종 점검은 `references/planning-checklist.md`를 따른다.
- DAG 검토가 필요하면 `references/dag-planning.md`를 읽는다.

## 문서 작성 규칙

- 핵심 의사결정과 실행 순서가 한눈에 보이게 쓴다.
- 추상 표현보다 검증 가능한 문장으로 바꾼다.
  - 나쁨: `성능을 개선한다`
  - 좋음: `검색 API P95 응답시간을 700ms에서 300ms 이하로 낮춘다`
- 범위와 비범위를 함께 써서 기대치를 고정한다.
- 일정, 담당자, 외부 의존성이 불확실하면 사실처럼 쓰지 않는다.
- 사용자가 별도 요청하지 않으면 장황한 배경 설명보다 실행 계획과 리스크를 우선한다.
- 문서 끝에는 필요한 경우에만 `결정 필요`, `지원 요청`, `다음 액션`을 남긴다.
- 큰 프로젝트에서는 반드시 `전체 계획서 -> 세부 계획 -> 리프 산출물` 추적선을 남긴다.
- 세부 플랜이 많아질수록 문서 자체보다 `의존성`, `산출물`, `완료 조건`을 더 엄격하게 쓴다.
- 개발 중 뒤늦게 드러날 가능성이 큰 쟁점은 별도 리스크나 오픈 이슈로 반드시 노출한다.

## 기본 출력 원칙

- 기본 형식은 Markdown으로 둔다.
- 기본 길이는 1~3페이지 수준으로 맞춘다.
- `검토용` 요청이면 쟁점과 가정을 더 적극적으로 드러내고, `승인용` 요청이면 의사결정 근거와 리스크를 더 분명하게 쓴다.
- 저장소 문맥이 있으면 해당 프로젝트의 용어와 섹션 이름을 우선 사용한다.
- 일정 표현은 영문 대신 `1단계`, `2주차`, `이정표 A`처럼 한국어 기준으로 쓴다.
- 대규모 계획은 단일 문서로 우겨넣지 말고 아래처럼 출력한다.
  - 전체 계획서 1개
  - 세부 계획 인덱스 1개
  - 세부 계획 문서 N개
  - 필요하면 DAG 요약 표 1개

## 참조 문서

- 템플릿이 필요하면 `references/plan-template.md`를 읽는다.
- 확인 질문과 점검표가 필요하면 `references/planning-checklist.md`를 읽는다.
- DAG 설계 규칙이 필요하면 `references/dag-planning.md`를 읽는다.
