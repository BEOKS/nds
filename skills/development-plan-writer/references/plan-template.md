# 개발 계획서 템플릿

필요한 섹션만 남기고 불필요한 항목은 삭제한다. 템플릿은 문서 길이를 늘리기 위한 목적이 아니라, 빠진 항목을 줄이기 위한 목적이다. 범위가 큰 프로젝트는 `전체 계획서 1개 + 세부 계획 문서 묶음` 구조를 기본으로 사용한다.

## 전체 계획서 템플릿

```md
# {프로젝트 또는 기능명} 개발 계획서

## 1. 배경
- 왜 이 작업이 필요한가
- 현재 문제 또는 기회

## 2. 목표
- 달성하려는 결과
- 성공 기준 또는 핵심 지표

## 3. 범위
### 포함 범위
- 이번 계획에 포함되는 작업

### 비범위
- 이번 단계에서 하지 않는 작업

## 4. 제약 및 전제
- 일정, 인력, 시스템, 정책 제약
- 확정 사항과 가정

## 5. 추진 방식
- 선택한 접근 방식
- 대안이 있었다면 간단한 비교와 선택 이유

## 6. 단계별 실행 계획
### 1단계
- 작업 항목
- 산출물
- 완료 조건

### 2단계
- 작업 항목
- 산출물
- 완료 조건

## 7. 일정 및 이정표
- 단계 또는 주차 기준 일정
- 주요 의사결정 시점

## 8. 의존성
- 선행 작업
- 협업이 필요한 팀 또는 시스템

## 9. 리스크 및 대응
- 리스크
- 영향도
- 대응 또는 우회 방안

## 10. 검증 계획
- 테스트 범위
- 확인 지표
- 승인 기준

## 11. 배포 계획
- 롤아웃 방식
- 모니터링 포인트
- 롤백 조건

## 12. 오픈 이슈
- 결정 필요 항목
- 추가 확인이 필요한 항목
```

## 세부 계획 인덱스 템플릿

```md
# {프로젝트명} 세부 플랜 인덱스

## 1. 문서 구성 원칙
- 세부 계획은 DAG 형식으로 연결한다.
- 순환 의존성은 허용하지 않는다.
- 리프 노드 산출물은 전체 계획서의 최종 산출물과 연결되어야 한다.

## 2. 문서 목록
| 문서 ID | 제목 | 상위 이정표 | 선행 문서 | 후행 문서 | 리프 여부 | 핵심 산출물 |
|---------|------|---------------|-----------|-----------|-----------|-------------|
| DP-01 | 예시 | 이정표 1 | - | DP-02 | N | API 명세 |

## 3. DAG 요약
- DP-01 -> DP-02
- DP-01 -> DP-03
- DP-02 -> DP-04

## 4. 전체 계획서 연결표
| 총괄 계획 이정표 | 연결 세부 문서 | 최종 확인 산출물 |
|----------------|----------------|------------------|
| 이정표 1 | DP-01, DP-02 | API 명세, 데이터 검증 결과 |
```

## 세부 계획 문서 템플릿

```md
# {문서 ID} {세부 플랜 제목}

## 1. 상위 연결
- 상위 이정표:
- 상위 목표:
- 연결되는 전체 계획서 산출물:

## 2. 범위
- 이 문서가 담당하는 범위

## 3. 선행 조건
- 선행 문서:
- 필요한 입력물:

## 4. 실행 계획
- 작업 항목 1
- 작업 항목 2

## 5. 산출물
- 생성 또는 변경될 결과물

## 6. 완료 조건
- 완료 판단 기준
- 다음 단계 인계 기준

## 7. 후행 연결
- 후행 문서:
- 다음 단계로 전달할 산출물:

## 8. 리스크 및 대응
- 리스크:
- 대응:
```

## 유형별 추가 섹션

### 신규 기능

- 대표 예시
  - 관리자 대시보드 신규 개발
  - 결제 취소 기능 추가
  - 검색 고도화 기능 출시
- 사용자 시나리오
- API 또는 화면 변경점
- 데이터 모델 영향
- 운영 알림 또는 FAQ 필요 여부

### 리팩토링

- 대표 예시
  - 회원 서비스 계층 정리
  - 공통 모듈 추출
  - 레거시 코드 구조 개선
- 현재 기술 부채
- 안전장치
  - 테스트 보강
  - 점진 전환 방식
  - 성능 또는 동작 회귀 확인 방법
- 중단 기준

### 마이그레이션

- 대표 예시
  - MySQL에서 Aurora로 이전
  - 온프레미스에서 Kubernetes로 전환
  - 세션 인증에서 토큰 기반 인증으로 이전
- 소스와 타깃 시스템
- 데이터 이전 범위
- 백필 또는 동기화 전략
- cutover 절차
- 실패 시 복구 경로

### 시스템 연동

- 대표 예시
  - 외부 결제사 API 연동
  - ERP와 주문 데이터 연계
  - 사내 시스템과 SSO 연결
- 외부 시스템 책임 범위
- 인터페이스 계약
- 장애 시 우회 경로
- 장애 시 우회 경로
- 인증/권한 이슈

### 운영 개선

- 대표 예시
  - 배포 파이프라인 자동화
  - 장애 알림 체계 개선
  - 운영 로그 표준화 및 수집 개선
- 현재 운영 지표
- 목표 SLI 또는 SLO
- 자동화 대상
- 알림과 runbook 변경사항

## 작성 요령

- 목표와 실행 계획 사이에 직접 연결이 보이게 쓴다.
- 일정 숫자를 쓸 수 없으면 `1주차`, `2주차` 또는 `이정표 A`처럼 상대 단위로 적는다.
- 리스크는 최소 3개까지는 억지로라도 써본다. 대부분 이 과정에서 빠진 전제가 드러난다.
- 승인용 문서는 선택 이유를 더 쓰고, 실무용 문서는 작업 순서와 완료 조건을 더 분명하게 쓴다.
- 대규모 프로젝트는 전체 계획서만으로 끝내지 말고 세부 계획 인덱스와 세부 계획 문서를 같이 만든다.
- 세부 계획 문서의 리프 노드 산출물을 합치면 전체 계획서의 최종 산출물이 완성되어야 한다.
