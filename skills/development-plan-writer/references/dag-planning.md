# DAG 기반 세부 플랜 작성 규칙

대규모 프로젝트는 세부 계획 문서를 단순 목록이 아니라 DAG로 구성한다. 각 문서는 독립적으로 읽을 수 있어야 하지만, 선후행과 산출물 인계 관계가 문서 간에 명확히 드러나야 한다.

## 핵심 원칙

- 전체 계획서는 `무엇을 왜 하는가`와 `최종적으로 무엇이 완료되어야 하는가`를 정의한다.
- 세부 계획은 `어떤 순서와 의존성으로 실행되는가`를 정의한다.
- 리프 노드는 반드시 검증 가능한 결과물을 갖는다.
- 모든 리프 노드 결과물은 전체 계획서의 목표 또는 최종 산출물과 연결되어야 한다.
- 사이클이 생기면 설계가 잘못된 것이다. 공통 준비 작업을 별도 선행 노드로 승격한다.

## 권장 문서 집합

### 1. 전체 계획서

포함 항목:

- 프로젝트 배경
- 최종 목표
- 범위 / 비범위
- 핵심 이정표
- 최종 산출물
- 주요 리스크
- 승인 또는 성공 기준

### 2. 세부 계획 인덱스

포함 항목:

- 세부 계획 문서 목록
- 각 문서의 ID와 제목
- 상위 이정표 매핑
- 선행/후행 관계 요약
- 리프 노드 여부

### 3. 세부 계획 문서

각 문서는 아래 항목을 가진다.

```md
# {문서 ID} {세부 플랜 제목}

## 1. 상위 연결
- 상위 이정표:
- 상위 목표:
- 연결되는 전체 계획서 산출물:

## 2. 목적
- 이 문서가 해결하는 범위

## 3. 선행 조건
- 선행 문서:
- 필요한 입력물:

## 4. 실행 내용
- 작업 1
- 작업 2

## 5. 산출물
- 문서, 코드, 데이터, 설정, 배포 결과 등

## 6. 완료 조건
- 검증 기준
- 인수 조건

## 7. 후행 연결
- 후행 문서:
- 다음 단계에 넘길 입력물:

## 8. 리스크
- 주요 리스크와 대응
```

## 리프 노드 설계 규칙

리프 노드는 더 이상 하위 세부 플랜으로 쪼개지지 않는 문서다.

- 리프 노드는 반드시 실제 산출물을 가진다.
- 산출물은 문서, 코드 변경, 마이그레이션 결과, 운영 설정, 테스트 결과 등 검증 가능한 형태여야 한다.
- 완료 조건은 모호한 상태값이 아니라 승인 가능한 기준이어야 한다.
- 각 리프 노드에는 아래 중 최소 하나가 있어야 한다.
  - 테스트 통과 기준
  - 배포 완료 기준
  - 운영 인수 기준
  - 사용자 검증 기준

## 전체 계획서 정합성 검증

아래 질문에 모두 답할 수 있어야 한다.

1. 각 세부 계획 문서는 어떤 전체 계획서 목표를 지원하는가
2. 각 리프 노드 산출물은 어떤 최종 산출물에 기여하는가
3. 전체 계획서의 모든 핵심 이정표는 어떤 세부 계획 문서들로 실현되는가
4. 세부 계획 전체를 완료하면 전체 계획서의 성공 기준을 충족하는가

하나라도 답하기 어렵다면 추적선이 끊긴 것이다. 문서를 다시 연결하거나 산출물 정의를 더 구체화한다.

## 간단한 예시

```text
MP-01 회원 통합 프로젝트
  ├─ DP-01 인증 체계 정리
  ├─ DP-02 사용자 데이터 정합성 정비
  └─ DP-03 서비스 전환 배포

DP-01 -> DP-02 -> DP-03
DP-01 -> DP-03
```

이 구조에서:

- `DP-01` 산출물은 신규 인증 규격과 API 계약
- `DP-02` 산출물은 정제된 사용자 데이터와 검증 리포트
- `DP-03` 산출물은 실제 전환 배포 결과와 운영 체크리스트

세 리프 산출물을 합쳐야만 `MP-01`의 최종 결과가 성립해야 한다.
