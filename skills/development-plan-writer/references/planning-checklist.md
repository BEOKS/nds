# 개발 계획서 체크리스트

## 계획서 작성 전에 확인할 항목

- 이 문서의 독자는 누구인가
- 이 문서의 목적은 승인, 정렬, 실행 중 무엇인가
- 이번 계획의 일정은 어떻게 되는가
- 포함 범위와 비범위가 나뉘어 있는가
- 외부 팀 또는 외부 시스템 의존성이 있는가
- 성공을 판단할 지표나 완료 조건이 있는가

## 필요 시 확인할 질문

정보가 부족하면 아래 항목을 순서대로 확인한다. 필요하면 전부 질문한다.

1. 목표가 무엇인가
- 해결하려는 문제와 기대 결과를 묻는다.

2. 이번 단계의 범위가 어디까지인가
- 반드시 해야 하는 것과 이번에 하지 않을 것을 나눈다.

3. 일정 또는 마감이 있는가
- 절대 일정이 없다면 단계 기반으로 적는다.

4. 의존성이 있는가
- 협업 팀, 외부 API, 인프라, 데이터 이전 여부를 확인한다.

5. 실패 시 영향이 큰가
- 롤백, 점진 배포, 모니터링 필요성을 판단한다.

## 문서 품질 점검

- 문서 첫 부분만 읽어도 왜 하는 일인지 이해되는가
- 목표가 측정 가능하거나 최소한 판단 가능한 수준인가
- 범위와 비범위가 분리되어 있는가
- 실행 계획이 작업 단위로 나뉘어 있는가
- 각 단계 또는 이정표의 완료 조건이 있는가
- 의존성과 선행 조건이 드러나는가
- 리스크마다 대응책 또는 관찰 포인트가 있는가
- 테스트 또는 검증 방법이 있는가
- 배포가 있다면 모니터링과 롤백이 있는가
- 확정 사항과 가정이 섞여 있지 않은가
- 오픈 이슈가 문서 말미에 정리되어 있는가

## 대규모 계획서 구조 점검

- 전체 계획서와 세부 계획 문서가 분리되어 있는가
- 세부 계획 인덱스가 존재하는가
- 세부 문서 간 선후행 관계가 DAG로 표현되어 있는가
- 사이클 없이 읽히는가
- 각 세부 문서가 상위 이정표와 연결되는가
- 리프 노드 문서마다 검증 가능한 산출물이 있는가
- 모든 리프 노드 산출물을 합치면 전체 계획서 결과물과 일치하는가
- 전체 계획서의 모든 핵심 목표가 세부 문서로 내려와 있는가

## 자주 고쳐야 하는 표현

- `추후 논의 예정`
  - 무엇을, 누가, 언제 결정해야 하는지로 바꾼다.

- `성능 개선 필요`
  - 어떤 지표를 얼마나 바꾸려는지로 바꾼다.

- `안정성 확보`
  - 테스트, 모니터링, 배포 전략으로 분해한다.

- `연동 대응`
  - 어떤 시스템과 어떤 계약을 맞추는지로 바꾼다.

## 마무리 규칙

- 정보가 불충분하면 빈칸보다 `가정`으로 남긴다.
- 자신 없는 사실은 단정형 문장으로 쓰지 않는다.
- 문서가 길어지면 배경보다 실행 단계와 리스크를 먼저 줄인다.
